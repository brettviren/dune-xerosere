* Research questions and decisions

This provides some decisions to the first 6 research questions and adds a new 7th.

** Q1 Providing detector geometry

#+begin_quote
How should detector geometry be provided to the edep-sim node and shared with
dissimilar downstream Phlex nodes that need different representations?
#+end_quote

- edep-sim will generate its own G4 geometry directly from a given GDML file.

- edep-sim will be made to not generate any ROOT TGeo.


** Q2 What issues are there for a Phlex detector geometry "resource"

#+begin_quote
Are there Phlex-level issues with the chosen geometry representation when it is
exposed as a Phlex "resource"? The same const geometry object would be delivered
to the node's function on every call.
#+end_quote

- Given Q1 decisions, this question is now only relevant only to TGeo consumers (not G4).

- We will delay implementing a TGeo Phlex "resource".


** Q3 Primary kinematics data model

#+begin_quote
What form should the primary-particle kinematics INPUT to the edep-sim node take
as an in-memory object (possibly produced by an upstream node), non-lossy w.r.t.
what Geant4 requires?
#+end_quote

- Adopt HepMC3 GenEvent with NuHepMC conventions.

- A GenEvent will be the type that is input to the node.

- Converters from other formats (eg Apache Arrow) are for future scope.

** Q4 Configuration delivery

#+Begin_quote
How should configuration be delivered to the edep-sim core through the edep-sim
Phlex node?
#+end_quote

- Embrace G4 macros as the sole configuration mechanism for edep-sim and recognize it is a control language.

- Categorize macro content by the edep-sim lifecycle phase that it is needed.  At least the categories "physics-list" (edep-sim construction time) and "physics-tunings" (pre =/run/initialize=).

- Reserve certain macro content to be generated by the Phlex node (eg, =/run/beamOn=)

- The Phlex node should validate any G4 macro text from the user against some rules.

- User G4 macro content is delivered to the Phlex node as normal Phlex
  configuration.  The user may directly provide multi-line text in Jsonnet or
  use Jsonnet's =importstr= if they prefer to keep macro text in separate files.


** Q5 Output data model

#+begin_quote
What should "the" edep-sim node output as Phlex data product(s)? Output is
variable: ionization energy deposits (→ TPC current waveforms downstream) and/or
scintillation photon hits (→ photo-detector PE), possibly both in one run, and
varying by detector type.
#+end_quote

Three layer output

  - MC-truth graph :: primaries + trajectory genealogy → HepMC (idiomatic,
    lossless; and symmetric with the Q3 HepMC/NuHepMC input). The step-point
    path is the one truth item HepMC can't type — keep it as an Arrow side-table
    if you need it.

  - Observables :: segments + photons → Arrow tables (the Q5 schemas), not HepMC.

  - Associations :: connect across the two layers via the keys that already
    exist: TrackId/ParentId (truth), Contributors/PrimaryId (observables →
    truth).  Represent as Arrow tables.

In implementing this output data model, we should attempt to disable edep-sim
from producing any of its existing ROOT output types.

** Q6 User hooks

#+begin_quote
How do we express which "user hooks" to use in configuration, and how does each
hook become a provider of data in the context of the edep-sim node?
#+end_quote

Still being investigated.


** Q7 Hooking up Phlex node with edep-sim kinematics generator instance (new research question)

The edep-sim kinematics generator instance is constructed by edep sim with a macro line like:

#+begin_example
  /generator/kinematics/external/loadGenerator <library> <symbol> <option>
#+end_example

There is also a 3-line variant that delivers each argument separately.  The
=<option>= is passed to the generator constructor.

A method is needed by which the Phlex node can pass GenEvent objects to the
generator instance.  There are three basic approaches so far:

1. edep-sim provides a method for the Phlex node to retrieve the
generator instance.  

2. A singleton registry is defined and the generator instance
self-registers its "this" pointer.  A registry key can be given to the
generator constructor in the <option>.

3. A singleton registry is used to hold "channel" objects (eg, something
with a std::deque<GenEvent>).  Phlex node constructs and registers a
channel instance and passes the registry key to the generator
constructor via <option>.

Comments:

- Case 1 may require changes to edep-sim if such a method does not yet exists.

- The singletons can be avoided by encoding a pointer to a string and passing it
  to the generator constructor via =<option>=.  The generator constructor would
  parse the =<option>= string into a =size_t= and reinterpret-cast that to a pointer
  to a suitable type.  In case 3, this "trick" would allow the registry to be
  omitted entirely and the "channel" object pointer passed directly.

- Regardless of the approach, the Phlex node must respect the edep-sim lifecycle
  and not attempt to exercise the communication conduit prior to it being fully established.

- Each option has repercussions on how to factor the dependencies (phlex,
  geant4, hepmc, edep-sim) across the packages we will implement.
