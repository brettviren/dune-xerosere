#+title: DUNE Xerosere project

DUNE Xerosere is the working title for a new DUNE software ecosystem.  Its
goals include support to run in the [[https://github.com/Framework-R-D/phlex][Phlex]] framework the [[https://github.com/WireCell/wire-cell-toolkit][Wire-Cell Toolkit]],
Geant4 via [[https://github.com/ClarkMcGrew/edep-sim][edep-sim]] and GPU accelerated optical physics with [[https://github.com/BNLNPPS/simphony][Simphony]] via the
[[https://github.com/Ningclover/edep-simphony-plugin][edep-sim / simphony plugin]] and other important, major packages relevant to DUNE.

* Name

The name is, of course, a play on the "DUNE" name.  From wikipedia:

#+begin_quote
A [[https://en.wikipedia.org/wiki/Psammosere][psammosere]] is the sequence of plant succession that has been initiated on
sand.  A psammosere is an intermediate stage in ecological succession, known as
a seral community, that begins life on newly exposed coastal sand. The most
common psammoseres are sand dune systems. Psammosere is a form of xerosere
succession, meaning it begins in an environment with limited to no freshwater
availability.

[[https://en.wikipedia.org/wiki/Xerosere][Xerosere]] is a plant succession that is limited by water availability. It
includes the different stages in a xerarch succession. Xerarch succession of
ecological communities originated in extremely dry situation such as sand
deserts, sand dunes, salt deserts, rock deserts etc. A xerosere may include
lithoseres (on rock) and psammoseres (on sand).
#+end_quote

Never explain a joke: When this project started, Phlex lacked "water" (all the
stuff needed to build applications on top of phlex) and dune-xerosere is the
process by which we grow an entire dune ecosystem.

The developer workflow itself has been abstracted into the reusable [[https://github.com/brettviren/xerosere][xerosere]]
command, which provides the "umbrella" that covers this new ecosystem.

* Goals

- Provide the actual integration of the suite of target packages with Phlex.

- Develop a "lingua franca" data model for DUNE in the Phlex era.

- Develop a "configuration layer" to bring uniformity across configurable Phlex algorithms.

- Develop patterns to manage complexity in Phlex and Wire-Cell configuration across the many DUNE detectors and types of jobs.

- Keep all packages well factored along lines of dependency while mitigating the complexity of developer workflow that such multiple, fine-grained packages can otherwise lead to.

- Develop and extract a portable development workflow that others can adopt and benefit from.

- Develop solutions to specific problems with an eye toward generality.

- Adhere to modular, portable design and avoid creating lock-in.

* Bootstrapping

This section describes one way to get to a point where the DUNE Xerosere
ecosystem can be built and run.  Similar bootstrapping can be done on, eg Alma 9
hosts.  Note, =/cvmfs/= mount is *not* needed nor involved.  Future work, likely
part of [[https://github.com/brettviren/xerosere][xerosere]] may allow leveraging packages provided by a CVMFS mount.

** OS

Debian 12 as one example.  Given the portability of the stack, other OSes should pose no particular problem.

#+begin_example
  # apt-get install -y \
      autoconf bash build-essential ca-certificates clang coreutils curl direnv \
      emacs extrepo fd-find gfortran git gpg jq less llvm locales lsb-release man-db \
      myrepos python-is-python3 python3 python3-click python3-setuptools python3-venv \
      python3-yaml ripgrep sudo unzip wget zip zlib1g-dev
  # extrepo enable mise && apt-get update && apt-get install -y mise
#+end_example

Inclusion of =mise= allows other modern tools to be used very easily.  If omitted,
some tools may require more specific installation instructions.

** Git

Clone this package.

#+begin_example
$ git clone git@github.com:brettviren/dune-xerosere.git dune/xerosere
$ cd dune/xerosere
#+end_example

Xerosere provides an =mr= (=myrepos=) file [[file:.mrconfig]] to aggregate and manage
the other various sources in this project.  The path =.mrconfig= will need to be
listed in your =~/.mrtrust= file.  Then, in a fresh clone of this package, run:

#+begin_example
$ echo "${PWD}/.mrconfig" >> ~/.mrtrust #If within dune/xerosere
$ mr co
#+end_example

This clones:

- The source for the actual packages covered by xerosere
- Spack and Spack package repos for WCT, Phlex and edep(sim)phony

Note: =mr= is not required nor is the particular layout or other conventions in
xerosere.  They are merely the conveniences that remain after other approaches
were considered and discarded.

** The =xerosere= command

Install the =xerosere= CLI.  Using the copy cloned under =python/xerosere= (editable,
so local changes to the tool apply immediately):

#+begin_example
$ uv tool install -e python/xerosere
$ xerosere --help
#+end_example

Alternatively install a released version directly:

#+begin_example
$ uv tool install git+https://github.com/brettviren/xerosere
#+end_example

=xerosere= is the single entry point for all developer workflows below (it
replaces the older =./umbrella= script; the two share the same on-disk layout).

** Configuration

=xerosere= reads a small, phased configuration.  Its built-in defaults already
encode this project's layout, so the only project-local setting needed is the
name of the active Spack environment.  Create =.xerosere/config.toml= at the
project root:

#+begin_example
[env.DEFAULT]
env_name = "gcc15"
#+end_example

This selects =extern/envs/gcc15/= (holding =spack.yaml= and its =view/=), with builds
under =builds/envs/gcc15/= and installs under =installs/envs/gcc15/= -- exactly the
locations the =./umbrella= default used.  Inspect the fully resolved parameters
with:

#+begin_example
$ xerosere config show
#+end_example

Additional =[env.<name>]= sections may define other environments or build
variants; select one for a given invocation with =--config-name <name>= (see
[[*Variant builds via git worktrees][Variant builds]]).

** Direnv

Xerosere provides a shell-independent direnv file [[file:.envrc]] to auto configure
a small amount of shell environment.  If not used, it still provides the
guidance on what shell environment must be configured.  Otherwise, see how to
[[https://direnv.net/docs/hook.html][hook]] direnv into your shell and then type:

#+begin_example
$ direnv allow
#+end_example

It is not required to use direnv and the =.envrc= file can be easily translated
into other environment setup methods.  =xerosere= itself also exports the same
Spack scope/cache isolation (so =~/.spack/= is never touched) when it runs Spack.

** Spack

Xerosere uses [[https://spack.readthedocs.io/en/v1.2.2/][Spack 1.2.2]] or perhaps newer.  The =mr co= clones the Spack source and the
direnv integration puts =spack= in your path and sets variables so that Spack will
not touch =~/.spack/=.  Everything ends up under =extern/=.  The full Spack shell
environment is not entered and in particular the =spack= command remains real and
not a shell function/alias.

#+begin_example
$ spack --version
1.2.2 (3e19345b6e12f5ff1b874f4059622fc6a1fd804a)
#+end_example

Spack is configured (via the =.envrc= file, and by =xerosere= directly) to *never*
write to =~/.spack/=.  It will instead use directories under =extern/scopes/=.

** CUDA

Best to use "system cuda" which may be under =/usr/= or =/usr/local/= instead of
having Spack build it which is fragile.  Before going on to the next section,
register your system cuda with:

#+begin_example
$ spack external find --scope user --not-buildable -p /usr/local/cuda-12.5 cuda
#+end_example
- =--scope user= writes to extern/scopes/user/packages.yaml (alongside your gcc/llvm externals).
- =-p /usr/local/cuda-12.5= points at the 12.5 toolkit so it doesn't grab the 11.8 on PATH.
- =--not-buildable= sets =buildable: false= for cuda, so Spack will never try the runfile again

However CUDA is provided, keep in mind that the version of nvidia driver for the
Linux kernel sets a range of CUDA toolkit version which sets a range of GCC
version which sets an upper bound for C++ standard version.  In some cases,
(CUDA 12.x with Phlex needing C++23) one must have two compilers, one to use as
a nvcc backend and one to compile C++23 code.  Xerosere Spack environments and
packaging support this compiler hybridization.

** Spack Environments

These are documented here

https://spack.readthedocs.io/en/v1.2.0/environments_basics.html
https://spack.readthedocs.io/en/v1.2.0/environments.html

Xerosere provides Spack Environment configurations in =extern/envs/*/spack.yaml=.
You can see the concrete spec and build the active environment (=gcc15=) with:

#+begin_example
$ xerosere spack concretize
$ xerosere spack install
#+end_example

These are thin wrappers over =spack= (targeting the environment named by
=env_name=) with some sane defaults.  Extra arguments pass through, eg =xerosere
spack install -j 32=.  For the full command reference:

#+begin_example
$ xerosere --help
#+end_example

* Developer tasks

** Update Spack packages for new versions

If you know the version, fastest is:

#+begin_example
$ spack -e extern/envs/gcc15 checksum -a edepsim 4.2.0
#+end_example

We leverage the spack env because the repo is registered with it.  It is
possible to register them global to the user scope with the following, but we'll
avoid that for now:

#+begin_example
$ spack repo add --scope user extern/repos/edep-simphony-spack/edep_simphony/spack_repo/edep_simphony
#+end_example

Evaluate the results by repeating the pair:

#+begin_example
$ xerosere spack concretize
$ xerosere spack install
#+end_example

** Local build

This builds local source under =devel/= via a "CMake super build" pattern.  So, it
only supports CMake-built packages.

#+begin_example
$ xerosere dev config
$ xerosere dev build
#+end_example

The active env is =gcc15= (from =.xerosere/config.toml=); builds go to
=builds/envs/gcc15/= and installs go to =installs/envs/gcc15/=.  =dev config= runs the
super-build configure (=cmake -S devel -B builds/envs/gcc15=) and =dev build= runs
=cmake --build= on it.  Both also accept a single package name to configure/build
it stand-alone (resolving its siblings from the install prefix), and pass extra
=-D= flags or cmake options through, eg:

#+begin_example
$ xerosere dev config wire-cell-toolkit -D WITH_EDEPSIM=yes
$ xerosere dev build  wire-cell-toolkit
#+end_example

By default, environment is not munged to use the build so use paths like:

#+begin_example
$ ./installs/envs/gcc15/bin/phlexed  --help
#+end_example

*** CMake variables and variants

Persistent =-D= flags for the whole super-build live in a =[cmake.<name>]= table
referenced from an =[env.<name>]= section via =cmake_config= (configure step) or
=cmake_build= (build step); each entry becomes a =-D<key>=<value>=.  On the command
line, =xerosere dev config -D FOO=BAR= passes extra defines through.

** Variant builds via git worktrees

To build one (or a few) =devel/= packages from a *different git branch* -- while
sharing the Spack view and every other package -- create a *variant*.  It uses a
git worktree for the varying package and its own build/install trees:

#+begin_example
$ xerosere dev variant add spng --pkg wire-cell-toolkit=spng
$ xerosere --config-name spng dev config
$ xerosere --config-name spng dev build
#+end_example

This checks out =wire-cell-toolkit= on branch =spng= into =worktrees/spng/=,
redirects only that package's super-build source there, and builds into
=builds/envs/gcc15-spng/= / =installs/envs/gcc15-spng/= against the shared =gcc15=
view.  A non-local branch is fetched fresh from a remote (=--remote=, default
=origin=); a branch that exists neither locally nor on that remote is an error
(add the fork's remote and retry).  Manage variants with:

#+begin_example
$ xerosere dev variant list
$ xerosere dev variant remove spng
#+end_example

** Spack develop

The =spack develop= scheme is *not* part of the =xerosere dev= workflow (which uses
the CMake super-build above).  It is available directly through Spack and is
*stateful* based on issuing the =develop= and =undevelop= commands.  It needs a
one-time =develop= registration over all packages to develop.  You may want to
use a different env than the nominal =gcc15= one.

#+begin_example
# fish syntax
$ for p in arrow-hdf dune-daq-types dune-daq-codec dune-daq-hdf dune-daq-arrow-frame-hdf \
         phlex-arrow-common phlex-arrow-hdf wire-cell-arrow wire-cell-phlex \
         wire-cell-phlex-arrow
    spack -e extern/envs/xerosere develop --path $PWD/devel/$p $p@main
  end
#+end_example

Then concretize:

#+begin_example
$ spack -e extern/envs/xerosere concretize -f
$ spack -e extern/envs/xerosere install -j 32
#+end_example

Doing =spack develop= mutates the environment to use the local clones instead of
pulling fresh from the git remotes.  To go back to the standard build:

#+begin_example
$ spack -e extern/envs/xerosere undevelop --all
$ spack -e extern/envs/xerosere concretize -f
$ spack -e extern/envs/xerosere install -j 32
#+end_example
